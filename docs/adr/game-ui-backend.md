# Game UI and Developer UI

Proposed in #299 for maintainer review before production backend work in #300. This ADR selects the direction and defines the boundaries for the opt-in spike.

## Decision

Build the player UI as a bounded native C++20 layer over SDL3 and the existing Vulkan renderer. Keep Dear ImGui as the Developer UI. The player layer owns screen, layout, style and focus state and produces ordered, clipped draw batches. Engine remains the host of both layers. Reuse the frame, allocation, shader compilation and retirement facilities already in the repo.

The hardest graphics requirements are integration with the existing swapchain, atlas reload, frame fences and SDR output. Even with a UI library, the game would still own those integrations and its session-aware navigation and input policy. Native layout, editing and accessibility carry a maintenance cost. The spike verifies drawing and basic focus only. The first shared controls and text field are the next evidence for the decision.

| Criterion | Native SDL3/Vulkan | RmlUi 6.3 | Nuklear 4.13.4 |
| --- | --- | --- | --- |
| Text and fonts | Existing baked face suffices for the spike. Production defines a text service over SDL3 and reusable font and Unicode components. | Default FreeType rasterization and fallback. HarfBuzz example provides a path to shaping via a custom font engine. SDL integration includes IME. | UTF-8 and built-in atlas or custom font callbacks. The host still supplies shaping and platform text integration. |
| Layout and style | Implement a small set of measured layouts and semantic style tokens. | Retained markup, RCSS styling and variables, flow and flex layouts. Strongest for larger screen sets and authored layouts. | Immediate-mode rows, templates and widgets. Application code still provides screen state and themes. |
| Focus, events, accessibility | Host owns routing, tab order, visible focus, keyboard activation and labels. Platform accessibility integration would require separate work. | Focus, navigation, forms and event propagation are built in. The host must integrate focus across surfaces and would need a platform accessibility bridge. | Widget input state and events. Host supplies tab policy, screen-level focus and platform accessibility. |
| Clip, textures, DPI | Dynamic scissors, generation-tagged atlas handles and one SDL logical-to-pixel transform. | Render interface supports geometry, scissor, clip masks and generated textures. Engine would supply rendering, texture resolution, DPI and event integration. | Draw command stream carries clip rects and image handles. | Vulkan 1.2 and MoltenVK | Uses the existing device and dynamic rendering path, with no additional device extensions. Versions are the evaluated upstream releases, with no imported source or packages. The RmlUi audit used upstream [6.3 release notes](https://github.com/mikke89/RmlUi/releases/tag/6.3), [license inventory](https://github.com/mikke89/RmlUi/blob/6.3/readme.md#license), [CMake options](https://github.com/mikke89/RmlUi/blob/6.3/CMakeLists.txt), [SDL/Vulkan sample](https://github.com/mikke89/RmlUi/blob/6.3/Backends/RmlUi_Backend_SDL_VK.cpp) and [HarfBuzz sample](https://github.com/mikke89/RmlUi/tree/6.3/Samples/basic/harfbuzz). Nuklear was evaluated from the [4.13.4 release](https://github.com/Immediate-Mode-UI/Nuklear/releases/tag/v4.13.4) and [upstream feature and license documentation](https://github.com/Immediate-Mode-UI/Nuklear/blob/v4.13.4/README.md).

The spike uses the repo-pinned ImGui 1.91.9 WIP source only to bake an independent copy of embedded ProggyClean glyphs on the CPU, plus a generated color sample. Dear ImGui and ProggyClean are MIT-licensed. The font source and attribution are in [imgui_draw.cpp](../../src/imgui/imgui_draw.cpp) and the library license is in [LICENSE.txt](../../src/imgui/LICENSE.txt). The spike owns its GPU atlas and uses its own draw pipeline, style and focus state. It adds no asset or package downloads. #302 will select and audit a production face. Any later shaping dependency must have an immutable version, license notices and a graphics-scoped build review before adoption. Graphics-off configures and links without any UI library.

### Native maintenance boundary

| Own in Game UI | Reuse at the boundary |
| --- | --- |
| Screen stack, focus traversal and navigation, and layout limited to rows, columns, fixed grids and scroll viewports | SDL3 for window events, committed text, clipboard and OS text input/IME integration |
| Design tokens, common control behavior, game widgets, inventory slots and their transient state | Existing image decoding and atlas publication. Adopt a font rasterizer and specialized text libraries when needed for font coverage, complex shaping or advanced Unicode behavior |

The first text service exposes measurement and drawing for UI labels and one bounded, single-line editor for existing game fields. It handles valid UTF-8, caret movement and deletion at valid character boundaries, selection, and SDL clipboard and committed text input. Fields retain the accepted values, size limits and validation rules of their Engine adapters. Display text uses the audited face and a visible missing-glyph fallback. The initial layout supports left-to-right text. Rich text, multiline editing, custom IME UI, bidirectional layout and complex-script shaping are follow-ups. Use SDL composition events where required for parity, and use a specialized library if grapheme segmentation or shaping becomes necessary.

During #301 and #302, evaluate one representative form with a text field, a scrollable list and a keyboard-operable modal. Check tab order, visible focus, clipboard and text input, focus restoration and the interaction tests below. Use ten engineer-days as the planning threshold for the shared layout, navigation, controls and text work across both issues, excluding #300 rendering and screen migration. If the scope estimate exceeds that threshold, or the form would require an in-house grapheme segmentation, bidirectional layout, shaping or platform IME implementation, reopen the ADR and compare an RmlUi version of the same form against the same input, renderer integration and resource criteria before expanding the native framework.

## Ownership and input

- **Engine** publishes a frame-scoped, immutable presentation model made of bounded player, inventory, session, roster, save/host status and settings views. Use the existing sim and network snapshots and presentation helpers. Shared fields can also feed Dev UI. Renderer/camera handles, mutable settings, Vulkan handles and debug telemetry stay in renderer or developer adapters. The current mixed `GameUIFrame` serves legacy ImGui during migration.
- **Game UI** owns navigation and transient widget state. Root is Main Menu without a session, HUD during a session and Loading during a transition. The stack adds Pause, Inventory, Settings, Host/Join and authorized administration screens, plus confirmation/error modals above them. Restore focus to a surviving opener on pop. Loading, leave, reconnect, projection resets and profile/world changes clear transient gestures and invalidate stale results by session epoch. Errors offer the existing retry, recovery or return path.
- **Typed actions** carry values such as `SelectHotbar(slot)`, `MoveStack(from, to)`, `OpenWorld(name, seed)`, `Connect(JoinRequest)`, `StartHost(Options)` and `SetVSync(enabled)`. An Engine-owned adapter validates context and dispatches at the existing frame boundary or queues actions for an existing safe point. Each intent uses one path to solo simulation, remote command queues, settings or the hosting supervisor. Keep authoritative acknowledgments and failures, including stale or rejected inventory and admin results. UI drag state is presentation only and local-only administration still uses verified capabilities. A UI screen cannot mutate inventory, server roles or world state directly.
- **Developer UI** owns ImGui docking, panel visibility, debug settings and `imgui.ini`. It is opt-in with F1 or `--dev-ui`. Engine retains simulation pause and cursor ownership. The scene projects across the full frame. The native HUD and dock-compatible screens anchor to the central dock area when visible, and use the full window when the workspace is hidden. A full-window native modal suppresses developer drawing and input. F1 can change the requested visibility during the modal, and dismissal applies that request using the existing dock layout.
- **One input router** handles application/window events first, then explicit globals, the top player modal or interactive screen, active developer widgets, and finally gameplay. A modal may veto view-changing globals. Global shortcuts are non-repeating and explicitly enumerated. A passive HUD never claims gameplay input. Pointer press fixes its owner through release, and only eligible key edges reach gameplay. Focus loss or ownership/capture changes cancel presses, transient drags and queued jumps, reset relative mouse deltas and require held gameplay inputs to release before rearming. Text entry, wheel and Escape each go to one owner. Escape dismisses the top modal/screen or opens Pause from HUD. Quit remains explicit. Solo pause uses the host suspension policy. Multiplayer menus suppress local controls while networking and server simulation continue.

## Frame and lifetime

Record scene, post and UI on the graphics command buffer that Engine hands to WorldRenderer. Use a positive viewport for top-left UI coordinates, intersect nested clips and clamp to the framebuffer before emitting scissors. Preserve the offscreen scene route as UI-free. Re-query logical window size and display scale separately from swapchain pixels, skip empty/minimized extents and use the same geometry transform for hit testing and paint. Player UI scale/accessibility preferences will be independent of developer layout preferences.

### Production composition contract for #300

Select the path from the existing `{VkFormat, VkColorSpaceKHR}` output-transfer policy. Game UI decodes sRGB-authored RGB, keeps coverage alpha linear, and submits premultiplied linear RGB with source-over blending (`ONE`, `ONE_MINUS_SRC_ALPHA`). The spike's opaque colors and cutout glyphs remain a separate proof.

| Swapchain | Scene and post | Game UI | Dev UI and present |
| --- | --- | --- | --- |
| sRGB + `SRGB_NONLINEAR` | Final composite or FXAA writes display-linear SDR directly to the sRGB swapchain attachment. With FXAA, the existing perceptual input is preserved and the FXAA result is decoded before output. | Load the swapchain attachment. Vulkan linearizes the destination for blending and encodes RGB on write. | ImGui renders last into the same swapchain image with its current pipeline and color convention, then present. |
| UNORM + `SRGB_NONLINEAR` | Final composite or FXAA writes display-linear SDR to a slot-local linear attachment. Composite skips its display encode. FXAA still receives the existing encoded perceptual input and decodes its result for the linear attachment. | Load and blend into the linear attachment. A fullscreen pass samples it and applies `linearToSrgb` once before writing to the UNORM swapchain image. | ImGui loads the encoded swapchain image and renders last using the existing UNORM pipeline and color convention, then present. |

The UNORM path adds one `R16G16B16A16_SFLOAT` attachment per frame slot, with color attachment, blend and sampling support verified during setup, and one fullscreen encode draw. That is about 31.6 MiB of image data at 1920×1080 for two slots, before allocator overhead. Report the actual allocation size separately from the atlas in #300. When Game UI has no draw work, use the existing direct post-to-swapchain path. Provision the extra images only for the UNORM Game UI path and reuse them across frames.

Order post writes before the Game UI attachment load and blend, with a color-attachment write to color-attachment read/write dependency. On UNORM, transition the linear target from color attachment to shader-read before the encode pass. The encode's swapchain write is ordered before the Dev UI attachment load. Reuse the slot only after its fence and recreate the attachments, views and encode descriptors at the existing swapchain recreation barrier. Keep swapchain acquire and present ownership in `VkFrameContext` and sample the linear target through its own view. These paths do not require swapchain sampling or an added steady-state wait. [Vulkan framebuffer blending](https://docs.vulkan.org/spec/latest/chapters/framebuffer.html#framebuffer-blending)

Before production widgets depend on this contract, validate both formats with FXAA on/off and Dev UI on/off. Sample constant swatches, overlapping colored quads and antialiased glyph edges against CPU linear source-over references. For example, 50% white over black should encode to approximately 188 in 8-bit sRGB, within one code value at the center of the swatch. Verify transparent pixels preserve the scene, Dev UI appears above Game UI, both output paths preserve scene and legacy ImGui appearance when Game UI is absent, and resize/recreate is clean under Vulkan validation. Exercise the format paths offscreen if the current surface cannot expose both formats.

The graphical UI renderer owns GPU font and UI atlas resources and bounded descriptor sets. World item icons are borrowed via generation-tagged texture handles resolved by the renderer, with stable item IDs in the model. Publish complete replacements between frames. Retire old buffers, views and descriptors after their last referencing fence, before destroying the underlying image. Batch by texture and scissor in paint order. Frame-local vertices/indices or instances may be written only after `VkFrameContext` waits that slot's fence. Swapchain recreation rebuilds a format-dependent pipeline at the existing idle barrier and resizes using the new extent. Device teardown uses the existing idle barrier. Texture reload or resize must not introduce steady-state queue/device idle calls or descriptor updates to a set in use.

## Verification and budgets

- Keep layout, navigation, action mapping and input ownership in plain C++ with no SDL/Vulkan/ImGui link in CPU-only tests. Inject font metrics and normalized window/pointer events. Cover fit, scissor intersection, 16:9/21:9, logical-to-pixel transform and scale change, keyboard traversal and activation, modal priority, focus/drag cancel, epoch changes, one-shot actions and solo/network outcomes. Reuse `InventoryUi`, `InputRouting`, `UiScale` and `MultiplayerUi` policies where their contracts apply. Prefer replayable deterministic inputs.
- #300 onward targets on the canonical physical GPU at 1920×1080, after warmup over 600 frames with identical seed, camera, VSync and scene settings. Measure p95 player UI build + record on CPU and timestamp delta on GPU with Dev UI closed. HUD targets ≤0.25 ms CPU, ≤0.20 ms GPU and ≤8 draws. Inventory/menu targets ≤0.50 ms CPU, ≤0.35 ms GPU and ≤32 draws. Record the device, driver, swapchain format, medians, p95 and draw counts.
- In #300, reuse the existing CPU and Vulkan profilers for independent `GameUIBuild`, `GameUIDraw`, `DevUIBuild` and `DevUIDraw` CPU scopes and separate Game UI and Dev UI GPU timestamps. Measure the UNORM encode separately and include its time and draw in the Game UI budget. Verify the two views can be attributed independently when both are visible. The Phase A spike shares the legacy ImGui draw scope.
- Bound player UI allocations to ≤1 MiB host upload per frame slot, ≤8 MiB per live owned atlas generation and ≤64 live UI descriptor sets including retired generations. Validate that repeated resizing, failure-atomic pack/scale reload and screen navigation reach a stable allocation plateau. Track shared scene atlas memory separately. Require zero steady-state UI GPU readbacks, waits or descriptor allocations. These are acceptance targets for later phases, with no new mandatory GPU CI.
- The #299 spike only tests the frame hook, one clipped texture sample, button, text, focus and resize. It is available from `ft_vox --seed 42 --ui-spike` and Escape closes the preview. A normal launch opens the legacy UI. The spike's input and draw code can be removed together when #300 takes over. See [migration and evidence](../game-ui-migration.md).

Player UI work covers the existing game flows. Full localization, platform accessibility certification, full controller support, generalized document/CSS layout, public hosting, renderer redesign and gameplay, save or wire changes are outside this epic.
